# Legacy directory backup compatibility

The new bundled-example provenance adapter made valid pre-provenance backups fail
`verifyBackup` and `restoreBackup`: their v1 inventory listed the old complete
adapter profile, while the importer required the new complete profile. This fix
admits that one explicit historical profile and preserves its payload bytes when
restoring into a new directory. It does not infer provenance from filenames,
titles or content, create a missing sidecar, or modify the original backup/library.

`RecoveryRegistry.backupRegistry(forDeclaredAdapters:)` accepts either the exact
current complete profile or the exact 13-adapter profile exported by frozen
`88ff6d6ce3471b9191b521dca6261fc8dde775e3`, with the same optional audited English
adapter configuration (14 historical adapters when enabled). It first rejects
duplicate declarations. Any other subset, unknown adapter or different English
configuration remains invalid. Future adapter growth must define another audited
rule rather than silently inherit this omission policy.

A historical package is captured and validated with its historical registry. A
new provenance store, its `.backup`, or a provenance tombstone fragment therefore
cannot be smuggled into an old-profile package. Exact schema/topology, unique JSON
keys, path/link checks, entry lengths/digests/totals, store decoding, identity and
source associations, and actual-payload equality remain enforced. No inventory
version or export schema changes. Re-exporting a restored legacy library writes
the current adapter profile while retaining the unchanged old payload and absent
provenance state. This validates a declared file-format contract; it does not
authenticate a historical producer or introduce signatures.

The regression packages were generated by the real frozen old exporter from its
own authored storage fixtures. The frozen production sources and original fixture
helpers were not changed. Two committed packages cover the standard and English
adapter profiles, 16 active format records, notes/progress, saved offline mock AI
and Japanese records, metadata and an old FB2 tombstone. The English-configured
package has no saved English-note payload; the existing English integration suite
separately covers saved English notes. These tiny Original assets are storage
fixtures, not proof of native document decoding/rendering. Generation details and
all 64 file SHA256 values are in `Fixtures/LocalRecoveryLegacy88FF/PROVENANCE.json`
and its README.

Validation on the changed package inputs:

- Before the product fix, both actual old-export profiles reproduced
  `.invalidPackage` under production commit `463020de7a0555265a2df21e878723220dd33ec6`.
- Related Swift run: **32 tests / 4 suites passed** (legacy compatibility, existing
  recovery, bundled provenance and English integration).
- Complete Swift run: **585 tests / 76 suites passed**. New compatibility coverage
  comprises three test methods with 21 argument cases: two historical restores,
  two current provenance round trips and 17 invalid-package mutations.
- Invalid cases include unknown/duplicate/missing adapter, configuration mismatch,
  duplicate entry, traversal, future/Boolean schema, unknown inventory field,
  corrupt original, invalid store, wrong source association, unknown store, and
  listed/unlisted/backup/tombstone provenance under a historical declaration.
  Verification and restoration both reject them, preserve the package and existing
  library, and leave no installed destination or staging directory.
- Exact original payload bytes and book/edition/hash/notes/progress are asserted,
  with current provenance backup/trash restoration still covered. No existing
  XCTest UI assertion or original Swift regression was weakened.

The first new regression run exposed an error in its directory-relative byte-map
helper; it compared incorrect relative keys across restored directories. The
helper now uses FileManager's relative-path enumerator. The byte-equality assertions
remain intact, and both failed and corrected run logs are preserved in the local
`BackupCompatibility/Evidence` directory. This was a test helper correction, not
a further relaxation of package validation.

All execution used the existing native heavy-check lock and self-authored temporary
fixtures. No GUI, production Library, personal backups, Keychain, real AI, security
settings or remote operations were involved. The old 463020d GUI/build evidence
remains historical. Product sources changed, so its compiled QA12 binary and GUI
results cannot be used as this fix's current GUI acceptance; a new immutable QA
snapshot and a new full gate12 followed by complete68 are required after the
morning unlocked desktop handoff. No publication, merge or push is authorized.
